Failure-impact validation experiments

This folder contains the research-only workflow for comparing Component 3's
predicted service and workflow failures with outcomes observed during a
controlled worker-node failure experiment.

The scripts do not inject failures, modify Kubernetes resources, or mount HTTP
routes in the application. `capture-prediction` performs one read-only request
to the running backend. `record-evidence` performs no network request.

## Required experiment order

Use this order for every run:

1. Confirm the backend is using the intended frozen workflow and live topology.
2. Capture the prediction while the cluster is still in its pre-failure state.
3. Perform the separately authorized controlled failure experiment.
4. Probe every expected service and workflow.
5. Record the observed results.
6. Run validation.
7. Evaluate all four research methods against the same observations.

Do not capture the prediction after failure injection. By then, rescheduling or
loss of cluster objects may have changed the topology, so it would no longer be
the prediction baseline for that experiment.

## Prerequisites

- Run commands from the repository root.
- Start the backend with `uvicorn app.main:app --reload`.
- Connect the application to the intended cluster.
- Use a real frozen workflow ID, worker-node name, and namespace.
- Decide the complete service and workflow probe set before the experiment.
- Obtain developer approval before any cluster-changing experiment action.

The scripts refuse missing, malformed, incomplete, or mismatched evidence. They
also refuse to overwrite existing artifacts.

## Build the pre-failure method comparison

Component 3 must compare the proposed cross-layer method with the three
planned research baselines:

1. replica-count-only analysis;
2. deployment-only exposure analysis;
3. dependency-only workflow analysis;
4. proposed cross-layer analysis.

Create this artifact before failure injection. The dependency-only scenario is
a service-failure hypothesis declared in advance. Never populate it from the
failures observed after the experiment, because that would leak ground truth
into the baseline.

### A. Capture the exact upstream graphs

The frozen-workflow endpoint returns an evidence envelope, so save its `graph`
member. The live-deployment endpoint already returns a bare `DeploymentGraph`.

```powershell
$baseUrl = "http://127.0.0.1:8000"
$runId = Read-Host "Unique experiment ID"
$workflowId = Read-Host "Frozen workflow ID"
$failedNode = Read-Host "Worker node selected for the experiment"
$namespace = Read-Host "Kubernetes namespace"
$dependencyScenarioService = Read-Host "Service declared unavailable in the dependency-only scenario"

$captureRoot = Join-Path (Resolve-Path ".\experiments\failure_impact_validation").Path "captures"
$runDirectory = Join-Path $captureRoot $runId
New-Item -ItemType Directory -Path $runDirectory -Force | Out-Null

$workflowPath = Join-Path $runDirectory "workflow-graph.json"
$deploymentPath = Join-Path $runDirectory "deployment-graph.json"
$comparisonPath = Join-Path $runDirectory "method-comparison.json"
$methodEvaluationPath = Join-Path $runDirectory "method-evaluation.json"

foreach ($path in @($workflowPath, $deploymentPath, $comparisonPath, $methodEvaluationPath)) {
    if (Test-Path -LiteralPath $path) {
        throw "Refusing to overwrite existing experiment artifact: $path"
    }
}

$escapedWorkflowId = [Uri]::EscapeDataString($workflowId)
$escapedNamespace = [Uri]::EscapeDataString($namespace)
$frozenWorkflow = Invoke-RestMethod -Method Get -Uri "$baseUrl/api/workflows/$escapedWorkflowId/frozen"
$deploymentGraph = Invoke-RestMethod -Method Get -Uri "$baseUrl/api/deployments/live?namespace=$escapedNamespace"
$workflowFreezeId = $frozenWorkflow.freezeId
$deploymentSnapshotId = $deploymentGraph.snapshotId

if ([string]::IsNullOrWhiteSpace($workflowFreezeId)) {
    throw "The frozen workflow response did not include freezeId"
}
if ([string]::IsNullOrWhiteSpace($deploymentSnapshotId)) {
    throw "The live deployment response did not include snapshotId"
}

$utf8NoBom = [Text.UTF8Encoding]::new($false)
$workflowJson = $frozenWorkflow.graph | ConvertTo-Json -Depth 100
$deploymentJson = $deploymentGraph | ConvertTo-Json -Depth 100
[IO.File]::WriteAllText($workflowPath, $workflowJson + [Environment]::NewLine, $utf8NoBom)
[IO.File]::WriteAllText($deploymentPath, $deploymentJson + [Environment]::NewLine, $utf8NoBom)
```

Stop if either request fails. Do not replace an unavailable frozen workflow or
live deployment with a sample graph.

### B. Generate the comparison artifact

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\run_method_comparison.py `
  --workflow $workflowPath `
  --deployment $deploymentPath `
  --failed-node $failedNode `
  --dependency-scenario-service $dependencyScenarioService `
  --output $comparisonPath
```

For a dependency scenario containing several services, repeat
`--dependency-scenario-service` once for each service. The generated artifact
records each method's evidence scope so a replica vulnerability is not
misreported as an observed service failure, and deployment-only analysis is not
misreported as a workflow prediction.

Inspect the comparison artifact before the failure. The experiment's service
probe scope must include every service claimed by any method, including static
`vulnerableServices`, deployment `unavailableServices`, and cross-layer
`failedServices`. The workflow probe scope must include the compared workflow.
If a claimed identifier cannot be probed, do not report method-level accuracy
for that run.

## 1. Enter the real experiment identifiers

Continue in the same PowerShell session used for the method comparison. The
following prompts declare the complete probe set before failure injection:

```powershell
$serviceName = Read-Host "Expected service to probe"
$workflowProbe = Read-Host "Expected workflow to execute"

$predictionPath = Join-Path $runDirectory "prediction.json"
$evidencePath = Join-Path $runDirectory "evidence.json"
$validationPath = Join-Path $runDirectory "validation.json"
```

Use a new `$runId` for every repetition. Do not reuse an existing artifact
directory for a different experiment.

## 2. Capture the pre-failure prediction

Run this before the controlled failure begins:

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\capture_validation_inputs.py `
  capture-prediction `
  --workflow-id $workflowId `
  --failed-node $failedNode `
  --namespace $namespace `
  --output $predictionPath
```

The command calls:

```text
GET /api/failure-impacts/runtime
```

It validates that the returned `workflowId` and `failedNode` match the requested
experiment before saving the prediction.

## 3. Conduct and observe the controlled experiment

Carry out the approved experiment through the team's controlled procedure. The
validation scripts intentionally provide no command that changes the cluster.

After the selected node failure, probe every service and workflow declared in
the experiment plan. Record only directly observed outcomes.

Accepted service result tokens are:

```text
SERVICE_AVAILABLE
SERVICE_UNAVAILABLE
```

Accepted workflow result tokens are:

```text
WORKFLOW_SUCCEEDED
WORKFLOW_FAILED
```

Unknown or unexecuted probes must not be marked as successful. An incomplete
probe set is rejected instead of being converted into a result.

## 4. Record post-failure evidence

Enter the real observed tokens:

```powershell
$serviceResult = Read-Host "SERVICE_AVAILABLE or SERVICE_UNAVAILABLE"
$workflowResult = Read-Host "WORKFLOW_SUCCEEDED or WORKFLOW_FAILED"
$observationSource = Read-Host "How the probes were captured"
$observedAt = [DateTimeOffset]::Now.ToString("o")
```

Then save the evidence manifest:

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\capture_validation_inputs.py `
  record-evidence `
  --experiment-id $runId `
  --failed-node $failedNode `
  --namespace $namespace `
  --observation-source $observationSource `
  --observed-at $observedAt `
  --workflow-freeze-id $workflowFreezeId `
  --deployment-snapshot-id $deploymentSnapshotId `
  --expected-service $serviceName `
  --service-result "$serviceName=$serviceResult" `
  --expected-workflow $workflowProbe `
  --workflow-result "$workflowProbe=$workflowResult" `
  --output $evidencePath
```

For multiple services or workflows, repeat both the corresponding
`--expected-*` and `--*-result` arguments. Every expected identifier must have
exactly one result.

The workflow freeze and deployment snapshot arguments are mandatory for this
research workflow. The method evaluator rejects evidence that omits the
deployment snapshot or names a different pre-failure topology.

## 5. Validate one experiment

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\run_validation.py `
  --prediction $predictionPath `
  --evidence $evidencePath `
  --batch-id $runId `
  --output $validationPath
```

The command prints the JSON result and writes the same UTF-8 JSON to
`$validationPath`.

## 6. Evaluate all research methods

Use the same complete evidence manifest to score the limited baselines and the
proposed cross-layer method. Run this only after all declared probes have real
results:

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\run_method_evaluation.py `
  --comparison $comparisonPath `
  --evidence $evidencePath `
  --output $methodEvaluationPath
```

The command verifies the failed node, deployment snapshot, experiment order,
and probe coverage. A method dimension that is not supported by that baseline
is exported as `null`; it is not counted as a correct empty prediction.

## 7. Validate repeated experiments

Create a batch manifest after completing two or more independent runs. Paths in
the manifest are resolved relative to the manifest file:

```json
{
  "batchId": "worker-failure-repeatability",
  "experiments": [
    {
      "prediction": "captures/run-01/prediction.json",
      "evidence": "captures/run-01/evidence.json"
    },
    {
      "prediction": "captures/run-02/prediction.json",
      "evidence": "captures/run-02/evidence.json"
    }
  ]
}
```

The identifiers and paths above illustrate the file structure only. Replace
them with the identifiers produced by the real experiments.

Run the batch:

```powershell
& .\.venv\Scripts\python.exe `
  .\experiments\failure_impact_validation\run_validation.py `
  --batch-manifest .\experiments\failure_impact_validation\batch.json `
  --output .\experiments\failure_impact_validation\batch-validation.json
```

## Reported metrics

The validation artifact reports service-level and workflow-level classification
counts and metrics:

- True positives: failures predicted and observed.
- False positives: failures predicted but not observed.
- False negatives: failures observed but not predicted.
- Precision: the proportion of predicted failures that were observed.
- Recall: the proportion of observed failures that were predicted.
- F1 score: the harmonic mean of precision and recall.
- Exact-match rate: the proportion of experiment runs where both the service
  failure set and workflow failure set matched exactly.

An undefined metric is exported as `null`; it is never replaced with a perfect
score. For example, recall is undefined when no positive failure was observed.

## Common errors

`Could not read ...`

: The path does not exist. Check it with `Test-Path $predictionPath` or
  `Test-Path $evidencePath`. Text such as `C:\full\path\to\...` is an example,
  not an existing file.

`Captured experiment is incomplete ...`

: At least one expected service or workflow has no observation. Run the missing
  probe and record its real result.

`Prediction and observation must refer to the same failed node`

: The prediction and evidence came from different experiment scenarios. Do not
  combine them.

`Method comparison and evidence must use the same deployment snapshot`

: The comparison and observation do not share the same pre-failure topology.
  Preserve both runs and repeat the experiment with matching inputs.

`claims were not probed`

: At least one baseline or cross-layer failure claim falls outside the declared
  probe scope. Run the missing probe; do not treat the missing observation as a
  successful service or workflow.

`refusing to overwrite ...`

: The output already exists. Preserve it and use a new experiment ID or output
  path.

HTTP `404`, `409`, `422`, `502`, or `503`

: The backend could not produce a live prediction. Resolve the frozen workflow,
  topology, node, cluster, or upstream evidence problem before conducting the
  experiment. Do not substitute sample data.

Expected input failures return exit code `2` with a concise `error:` message.

## Automated checks

```powershell
.\.venv\Scripts\python.exe -m pytest `
  tests\failure_impact_prediction\test_validation_input_capture.py `
  tests\failure_impact_prediction\test_validation_runner.py `
  tests\failure_impact_prediction\test_validation_batch_runner.py `
  tests\failure_impact_prediction\test_method_evaluation_runner.py `
  tests\failure_impact_prediction\test_method_comparison_guide.py `
  -v --basetemp .pytest-tmp-validation-guide
```

These tests use controlled in-memory data. Passing tests verify the workflow
implementation; they are not evidence that a real cluster experiment succeeded.
