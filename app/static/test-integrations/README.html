Add application test evidence

Keep using your application's tests. Export the selected execution and request trace IDs, import the JSON in Add Test Evidence, then add its observed calls to the current workflow. Test files are not discovered through Kubernetes.

Run an existing HTTP workflow probe

Upload an existing probe with this wrapper. The engine uses its existing http_sequence runner. Each step needs explicit expected status codes; the definition needs an explicit terminal success condition. These checks do not establish dependency necessity.

{
  "testName": "Your existing test name",
  "applicationUrl": "http://your-approved-application-host:port",
  "entryService": "your-discovered-kubernetes-service",
  "executionDefinition": {
    "runnerType": "http_sequence",
    "measuredStep": "open-page",
    "steps": [{"name": "open-page", "method": "GET", "path": "/your-path",
               "expectedStatusCodes": [200], "responseContains": ["your actual response marker"]}],
    "successCondition": {"protocol": "http", "terminalService": "your actual trace service name",
                         "operationName": "your actual span operation", "httpStatusCodes": [200]}
  }
}

Use your actual target, requests and assertions; the example is a format description, not a supplied test case. Run sends application traffic and may have application-side effects. The target must be reachable from the engine backend and allowed by WORKFLOW_TARGET_ALLOWED_HOSTS. In the extension, host services commonly need host.docker.internal with operator configuration. No allowlist or network policy is changed by import.

Pytest

Download the Python helper into your test project. Pass a fresh e.headers() to each HTTP request. Keep the whole test's assertions inside the context. Write one export per execution (including retries/parameterizations).

from pytest_evidence import Evidence

def test_existing_flow(request, tmp_path):
    e = Evidence(request.node.nodeid, "YOUR_NAMESPACE", APP_URL, ENTRY_SERVICE)
    try:
        with e:
            response = your_http_client.get(APP_URL + EXISTING_PATH, headers=e.headers())
            ok = YOUR_EXISTING_ASSERTION(response)
            e.assertion("Your existing business assertion", bool(ok))
            assert ok
            # If supplied, select the actual outcome request and success condition:
            # e.outcome_trace(e.execution["traceIds"][-1])
    finally:
        e.write(tmp_path / (e.execution["executionId"] + ".json"))

Provide success_condition=... using the terminal contract above and select an outcome trace when you want trace-based success evaluation. Without it, the runner report is retained and the engine's outcome stays indeterminate.

Playwright

Download the Node helper. Attach before navigation, scope the browser context to one test execution, and export in finally. It instruments document/fetch/XHR requests to the declared application origin only; use e.headers() explicitly for APIRequestContext requests or additional application origins. Cross-origin CORS policy and service workers can prevent interception; the helper does not bypass either.

import { Evidence } from './playwright-evidence.mjs';

test('your existing test', async ({ context, page }, testInfo) => {
  const e = new Evidence({ testName: testInfo.titlePath.join(' / '),
    namespace: 'YOUR_NAMESPACE', applicationUrl: APP_URL, entryService: ENTRY_SERVICE });
  const detach = await e.attach(context);
  let status = 'failed';
  try {
    // Your existing navigation and assertions go here.
    await page.goto(APP_URL + EXISTING_PATH);
    await YOUR_EXISTING_ASSERTIONS(page);
    e.assertion('Your existing business assertion', true);
    status = 'passed';
  } finally {
    await detach();
    await e.write(testInfo.outputPath(e.execution.executionId + '.json'), status);
  }
});

Trace correlation and import

Your application must already emit OpenTelemetry spans and honor incoming W3C traceparent. The helpers assign separate trace IDs to requests; they do not install tracing. The engine fetches only those exact IDs from its configured Jaeger query endpoint. You may instead include normalized Jaeger trace objects in the export's traces array, allowing import without a tracing query connection.

Raw JUnit XML, a Pytest results file or a Playwright trace.zip alone is insufficient: these do not identify distributed service traces. Export execution name/ID, target, timezone-aware start/finish, request trace IDs and assertions with the helper or an equivalent CI adapter. Missing traces, propagation failures, sampling and ingestion delays remain explicit. Refresh traces never reruns a test. Imported reports are developer-supplied evidence, not cluster attestation.

Trace names are matched exactly to discovered logical Kubernetes services. If names differ, add explicit serviceMap entries in Advanced settings. Unmatched names remain visible. Separate requests are not connected by invented call edges.

Optional dependencyDeclarations on an execution may list source, target and Mandatory/Optional/Supporting/Unknown labels from your test specification. They remain declared suggestions. Imports preserve current labels; differing declarations require visual review. Imports cannot create or overwrite experimental validation. A successful execution does not prove that every observed dependency is mandatory.

Limits: 10 executions, 20 trace IDs per execution, 30 total IDs, and 8 MiB per import. No arbitrary Python/JavaScript is executed by the engine. Current integration uses normalized Jaeger data; other runner/telemetry formats require an adapter.

Runner integration references: Playwright request interception and Pytest fixtures.
